# 资料缺口与状态输出修正

抽取与覆盖提示词明确区分：本次分析资料未收齐/未提供并非业务发现；明确违反法定、监管或内部报送义务的发现仍需保留。字段核验对 issueDescription/problem/specificMatter 同样检查业务事项性质，不能仅因逐字引用资料缺口说明而通过。该判别依赖模型，非关键词硬删除；混合段落中的真实问题继续提取。

rectificationStatus 要求输出简明业务状态。后端仅对明确完整同义值做规范化，例如已全部完成→已完成、正在整改→进行中，保留原quote，并记录 STATUS_NORMALIZED。不以“完成”子串判断状态，计划/否定/冲突不会因此变成完成；未完成但阶段未知不推成未开始。Pi 对既有同义值也作精确映射，不能解释的值继续 PENDING_REVIEW。

在明确的 internal.daily.litigation 规则下，模型遗漏/未确定 factType 时补为 LITIGATION，记录 FACT_TYPE_FROM_LITIGATION_RULE；internal.accountability 且存在 accountabilityAction 时补为 ACCOUNTABILITY。其他情况显式输出 UNSPECIFIED，保留旧默认值对应的候选哈希，不按关键词臆测类型。

这些变化没有改动评测标准答案。字段描述仍须保留必要的主体、时间和经过，不为严格字符串得分删除业务信息。发布代码后重启服务，清空旧进程缓存。

## 公开材料发现的问题修复

- LightParser 对可识别的有边框 PDF 表格保留行、列和合并单元格，输出既有 Table IR。单元格内排版换行规范化；表格外正文、页码和块顺序保留，避免表格正文重复进入普通段落。不明确的表头不删除，无法完整覆盖文字的表格回退到正文解析。
- 抽取与漏项复查显式要求 factType；正文一级问题逐项拆分，整改对照表按业务行保留完整事项，分别处罚的机构逐机构输出。同名但职务不同的责任人不合并。
- 已列问题后的汇总法律依据、监管措施和共同整改要求不另计为新问题；只在规则提供对应字段时附入已有事项。
- 正常经营/关联交易披露、统计合计不能作为监督问题；“临时公告未披露的事项”栏目本身不代表违反披露义务。抽取与字段核验同时约束。
- 整改状态核验区分“执行了措施”与“问题已经解决”；计划不足以认定未开始，印发制度/开展检查不足以认定整体已完成或部分完成。明确整体完成或原问题直接消除的事实仍可通过。

旧 PDF 的已存 IR 不会自动改变。上线后需通过现有重新解析、版本和索引流程处理旧资料，不能直接改写库中的历史 IR 或引用。该表格能力不等于扫描件 OCR 或所有无边框表格都已支持。公开材料复测仅覆盖冻结页面/案例范围，未经独立人工标注复核，不代表 Java、数据库和报告端到端验收。

## 整改状态统一及核验返回防错

抽取、补漏、核验均通过 `prompting.load_prompt` 加载同一份 `status-policy.txt`。部分对象已解决、其他对象仅提交申请而结果未知时，不据此判部分完成；明确剩余仍未解决才支持部分完成。原文明确尚未完成时仍可保留合法的粗粒度状态“未完成”，不要求额外知道启动阶段。缺少状态不影响保留已知措施、数量和结果。

抽取缓存键包含实际拼接后的完整提示词，状态规则变化使旧缓存失效；公开材料评测的 promptHashes 同样计算拼接后的完整提示词，包含共享规则，不再只计算单一提示词文件。

核验响应出现漏ID、重复ID或未知ID时最多重试一次；出现“故/因此/所以不支持”等明确否定结论却返回 supported=true 时同样最多重试一次。第二次仍不合法则报错，不返回可通过的结果。此检查只处理可识别的结构错误及明确矛盾表述，不替代语义核验。

`pipeline/tests/fixtures/supervision_status_contrasts.json` 保存16个合成状态对照样例及预设标签，覆盖申请结果未知/明确待批、部分/全部收回、措施与解决结果、计划/未启动、未完成及跨事项引用。它不是客户或公开原始文书，不代表真实材料分布；标签不得传给模型。实际调用结果与中间失败单独留存于工作区外部评测目录。

## 2026-09-10 扫描件与无边框表格修复

- PDF 页内单张图像覆盖页面至少75%时，即使附有可提取文字，也转入扫描件流程，避免继续信任损坏的隐藏文字层。这是保守的扫描识别规则，可能增加整页背景图文档的OCR开销。
- 已配置 `PIPELINE_OCR_BACKEND=mineru` 时，生产解析及公开材料评测均走OCR兜底。MinerU明确使用 `parse_method=ocr`。未启用OCR仍返回E202，不假装解析成功。
- Windows FastText权重位于中文路径时，自动复制到ASCII缓存目录，按内容哈希命名并核对内容；不改安装包和原权重。默认使用临时目录，可用 `PIPELINE_OCR_MODEL_CACHE` 指定可写的ASCII目录。
- 引用不逐字匹配时，最多追加一次仅修复引用的模型调用（model_attempts=2）；接口不允许返回业务value，原值由程序保留。来源限当前证据组，已有效引用不得丢弃，修复不通过仍报错。
- PDF交错列引用允许拆成多条：每行必须在同一PAGE_TEXT证据内逐字、唯一、按顺序出现。不改字、不调序、不把不同证据拼成一条原文。该机制只校验引用位置，语义仍须后续核验。
- 只含issueDescription、rectificationStatus、evidenceLocation且非问责章节的规则，排除额外ACCOUNTABILITY候选并记录原因；问责章节及含专用字段的规则保持独立问责抽取。
- 评测评分v1.2识别规范的全角千分位逗号（10，338）；不拼接格式错误的数字、不忽略正负号。标准答案未修改，历史结果保留。

部署后需重启服务，并通过既有流程重新解析有问题的旧PDF；新代码不会自动替换历史IR。测试中的公开材料通过不等于Java上传、数据库、报告生成全链路已验收。

问责字段补充约束：处分字段不重复已单列的姓名；关联事项保留有明确同事件依据的共同背景和总体规模，并明确合计口径，不将总体金额赋给单个责任对象。漏项检查格式失败时，重试提示明确只允许三个顶层数组键；仍保留原有严格校验和重试上限。
